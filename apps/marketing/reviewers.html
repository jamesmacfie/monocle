Install

For Web Store reviewers

What it does, what it touches, and why.

This page is written for Chrome Web Store and Firefox AMO reviewers. It states Monocle's single purpose, justifies every permission, and documents the security model — including residual risks we track openly rather than hide.

Single purpose

Monocle is a command palette for the browser. It provides one keyboard-driven interface to launch actions across tabs, history, bookmarks, downloads, settings, and user-defined automations — like VS Code's command palette or macOS Spotlight. It renders in two contexts (a keyboard overlay on any page, and a new-tab replacement), but everything serves that single function: launching commands.

Permissions

Monocle installs with a minimal required set and requests everything else on demand, the first time a user runs a command that needs it.

Host permissions

Exactly two external hosts, both image-only:

  • https://api.unsplash.com/* — random landscape photo for the new-tab background. Optional; new-tab override can be disabled.
  • https://icons.duckduckgo.com/* — favicons for bookmark/history rows, used only after the underlying permission is granted.

There are no other network endpoints. No telemetry, no analytics, no data-collection host.

Enforcement

Permissions are gated at two points: the UI shows a grant affordance next to protected commands, and the background re-checks each required permission with permissions.contains() immediately before execution. Browser truth always wins over cached UI state, so a revoked permission blocks execution even if the UI is stale.

Site SDK security model

The window.Monocle SDK lets pages register session-only, non-privileged commands. It is a runtime command source with strict containment — not a permissioned plugin system.

Sites can

  • Register actions, groups, forms, and search pages their own JS could already perform.
  • Set custom icons, descriptions, and URL-visibility rules.

Sites cannot

  • Request permissions or bind global keybindings.
  • Reach browser APIs (tabs, bookmarks, history, cookies…).
  • Run arbitrary JS in the extension context or persist state.

Containment

  • No direct channel. Pages can't sendMessage to the extension (no externally_connectable); the only path is postMessage to an isolated content bridge that accepts just two message types.
  • Commands run in the page. On selection, the extension asks the page to invoke its own callback by id; it never runs page-supplied logic itself.
  • Closed shadow DOM. The palette renders in a closed shadow root, so page JS can't inspect it or read bookmark/history data shown in it.
  • Double validation. Registrations are validated in the bridge and again when callback-returned commands arrive.

Caps & validation

Every declaration passes a strict Zod schema before the extension sees it: unknown fields rejected, reserved generated-action ids protected, ≤20 registrations per page, ≤100 commands per tree, ≤5 nesting levels, icon URLs limited to http(s), and SVG icons hardened (no <script>, no inline handlers, no external resource loads, ≤10,000 chars).

Input & message validation

  • Sender checks. Every UI→background message is sender-validated — messages from other extensions, or from data: / javascript: / about:blank URLs, are rejected.
  • Schema checks. Messages are validated against a Zod discriminated union; unknown message types never reach a handler. Context requires a non-empty url.
  • Documents are data, not code. Automations and snippets are validated at save, at import, at the message boundary, and structurally again at run time. There is no eval, no new Function, and no arbitrary-JS step anywhere in the codebase — by policy.
  • Workflows are fixed verbs. Content workflows validate against a closed step schema; unsupported steps fail loudly rather than silently.
  • Keybindings & URL rules. Validated to a canonical format and safe pattern syntax before persisting.

Data handling

Stored locally only

Command settings, favorites, local usage stats (for ranking), snippets, automation documents, feature config and runtime state, and transient surfaces — all in chrome.storage.local. No sync storage, no cloud.

Not collected

No telemetry, no analytics, no profiling, no login, no off-device user-data flow. The two external hosts serve images only. Page context (the current URL/title) is used to filter commands and never leaves the device.

Documented residual risks

The codebase documents these honestly in docs/site-sdk-security.md. None grant a hostile page access to browser APIs or user data through privilege escalation; they are edge cases we track with mitigations in progress.

RiskPosture
Synthetic key events could fire registered keybindingsPermissioned and confirm-gated commands are still protected; an isTrusted guard is a tracked fix.
Extension fingerprinting via window.MonocleDetectable at document_start; per-origin gating is under consideration.
Icon-URL tracking beaconRestricting URL icons to the registering origin / no-referrer is tracked.
Favicon lookups leak domains to DuckDuckGoOnly after the user grants bookmarks/history; local favicon sources are under consideration.
Trusted-UI injection / palette spamBounded registrations and a 1,000 ops/minute rate limit prevent abuse; clearer SDK-row badging is tracked.

A second tier of latent weaknesses (e.g. client-supplied context.url treated as advisory, not a security boundary) is also documented as defense-in-depth — none are reachable by pages today.

Notes for review

  • Page SDK is data, not code. Pages post declarative descriptors; the extension validates and wraps them and runs the page's own stored callback by id. No eval, new Function, or CSP relaxation anywhere — verifiable by repo-wide search.
  • Two <all_urls> content scripts. A keyboard-summoned palette must exist everywhere: one script injects the closed-shadow-DOM palette; a minimal MAIN-world shim installs window.Monocle and relays validated messages to the isolated bridge.
  • The global key listener is not a keylogger. It suppresses only keystrokes matching the registry or a sequence prefix; all other input flows to the page, and nothing leaves the device.
  • Local-only data. The new-tab page and its scripts are fully local; only the background photo and favicons are remote images.

Full detail lives in the repository docs: site-sdk-security.md, site-sdk.md, store-submission.md, permissions.md, and messaging.md.
