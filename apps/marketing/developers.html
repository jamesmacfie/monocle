Developer reference

How Monocle is put together.

Monocle is a WXT extension in TypeScript, React, and Redux. The background service worker owns everything privileged; the UI renders plain suggestion data and talks to the background over a validated message protocol. This page walks the architecture, the data flows, the schema, and the wire format.

Architecture

The same React command palette runs in two contexts, plus an options page. A single background service worker is the source of truth.

Ownership boundaries

Background owns

Command definitions and executor functions · all browser API access · settings persistence · permission grants and checks · the keybinding registry · workflow forwarding · automations and triggers · feature modules and state · surfaces.

UI owns

Rendering Suggestion values (never executable functions) · local Redux for navigation, search, and form values · capturing keystrokes and forwarding them · sending typed messages. Shared components must work in both the closed shadow DOM and normal document DOM.

Redux store

Each palette mode mounts its own store from a shared factory. Key slices: settings (theme, new-tab prefs, permission mirror), navigation (page stack, search values, child commands, inline form values), commandPalette (overlay visibility), keybinding (capture state), settingsCatalog, snippets, automations, and features for the options page.

Core data flows

Command loading, search & execution

  1. UI sends monocle-commands-get { context } on mount; the background loads root commands, applies browser/context compatibility and URL filtering, computes favorites, ranks, and returns Suggestion[] for the empty state.
  2. Typing (debounced ~200 ms) sends monocle-commands-search { query, parentPath?, seq }; the background scores an in-memory, URL-filtered search index incrementally and returns the top-N, with deep-search matches inline. Stale seq responses are dropped.
  3. Selecting an action/submit sends monocle-command-execute { id, context, formValues? }; the background resolves the node, checks merged permissions, runs the executor, and records usage.

Nested navigation

  1. Selecting a group or search sends monocle-command-children-get; the background resolves dynamic children (or search results) and converts them to suggestions.
  2. The navigation slice pushes a new page with the children, a reset search value, and inherited form defaults. Escape pops it and restores the prior search state.

Keybindings

  1. A global keydown outside editable elements is normalized to a canonical string (<cmd-shift-k>) and sent as monocle-keybinding-execute.
  2. The background registry resolves exact matches or sequence prefixes, scoped per sender tab + document, with an 800 ms chord window. A match executes through the same command path, or opens the palette at that command.

Workflow forwarding

  1. A command or the automation engine calls monocle-workflow-execute { workflow, context, tabId? }; the background resolves the target tab, validates against the workflow schema, and forwards monocle-workflow-content-execute to the tab.
  2. The content executor in content/workflow/ runs each step and returns a WorkflowResult (including getText extractions) back up the chain.

Surfaces (declarative UI)

  1. A feature, automation, or command writes to the owner-namespaced surfaces store; every mutation broadcasts monocle-surfaces-changed.
  2. Each SurfaceHost queries monocle-surfaces-get { url }, renders the kinds it owns (overlay/modal/picker in content, badge on the new tab), and reports interactions via monocle-surface-action. dismiss removes the surface; any other action routes to the owner's handler.

The command schema

Commands are typed CommandNode values — a discriminated union on type. The UI never receives these; it receives Suggestion values converted in the background, with execute, children, and getResults functions staying server-side.

TypeBehavior
actionExecutable command. Checks permissions, optionally confirms, runs, records usage.
submitForm button. Collects sibling input values, validates, executes.
groupDynamic container; selecting opens a child page. May opt into deep search.
searchDynamic search page; typing re-fetches results from the background.
inputOne inline form field; value lives in navigation form state.
displayStatic, non-executable row for headings and empty/error states.

Shared fields

type CommandNode = {
  id: string                       // stable, kebab-case; favorites/settings/binding key
  type: "action" | "submit" | "group" | "search" | "input" | "display"
  name: AsyncValue<string | string[]>   // array = breadcrumb for deep-search rows
  description?: AsyncValue<string>
  icon?: AsyncValue<CommandIcon>   // lucide | url | svg
  keywords?: AsyncValue<string[]>
  permissions?: BrowserPermission[]      // inherited by group children
  urlRules?: { allowUrls?: string[]; denyUrls?: string[] }
  supportedBrowsers?: ("chrome" | "firefox")[]
  keybinding?: string              // author default, e.g. "<cmd-t>"
  keybindingBehavior?: "execute" | "openPaletteAtCommand"
}

type AsyncValue<T> = T | ((context: Browser.Context) => Promise<T>)

Most display fields are an AsyncValue — a literal or a function of context, resolved once per palette fetch. Keep resolvers cheap; they run together in a Promise.all.

Form fields

A form is a group of input nodes plus one submit. Field variants: text, textarea, select, checkbox/switch, multi, text-list, color, and number. Text-like fields store strings; multi and text-list store arrays in UI state and are comma-joined for older executors.

Message protocol

UI → background goes over chrome.runtime.sendMessage; background → tab goes over chrome.tabs.sendMessage. Every message is sender-checked and validated against a Zod discriminated union; handlers return { error } rather than throwing.

MessageDirDoes
monocle-commands-getUI→bgRoot empty state: favorites + ranked suggestions.
monocle-commands-searchUI→bgScored, sequenced search results with deep matches.
monocle-command-children-getUI→bgResolve a group's children or a search page's results.
monocle-command-executeUI→bgPermission-check and run a command with form values.
monocle-keybinding-executeUI→bgResolve a keystroke against the registry / sequences.
monocle-permission-request · monocle-permissions-getUI→bgRequest an optional permission; read current grants.
monocle-command-setting-updateUI→bgPersist keybinding, hidden, or URL-rule changes.
monocle-workflow-executeUI→bgValidate and forward a workflow to the target tab.
monocle-workflow-content-executebg→tabRun workflow steps in the content executor.
monocle-surfaces-get · monocle-surface-actiontab↔bgFetch URL-matched surfaces; report interactions.
monocle-features-get · monocle-feature-config-update · monocle-feature-action-executeUI→bgRead feature descriptors, persist config, run actions.

The context object rides on most messages: 

interface Context {
  url: string                  // non-empty, required
  title: string
  modifierKey: "shift" | "cmd" | "alt" | "ctrl" | null
  isNewTab?: boolean
}

Storage

Everything is chrome.storage.local — no sync, no cloud. State is split across independent keys so features evolve separately.

KeyHolds
monocle-settingsTheme, new-tab prefs, and per-command settings (keybinding, hidden, urlRules).
monocle-favoriteCommandIdsFavorited command ids.
monocle-commandUsageUsage stats for ranking (90-day auto-cleanup).
monocle-snippetsSaved snippets.
monocle-automationsAutomation documents.
monocle-feature-config / -stateDurable feature config and transient runtime state, keyed by feature id.
monocle-surfacesOwner-namespaced declarative surfaces (session owners cleared on startup).

updateCommandSettings shallow-merges top-level fields but deep-merges urlRules one level, so updating an allow list preserves the deny list. Empty entries are pruned.

The window.Monocle site SDK

Any page can register session-only, non-privileged commands. The page posts declarative descriptors to an isolated content bridge, which validates them and hands the background extension-owned CommandNode wrappers. Callbacks stay in the page; only string callback ids cross the boundary. 

const handle = window.Monocle.commands.register({
  namespace: "docs",
  name: "Docs",
  icon: { type: "lucide", name: "BookOpen" },
  commands: [{
    id: "open-search",
    type: "action",
    name: "Open Site Search",
    placement: "root",
    actionLabel: "Open",
    onExecute() {
      document
        .querySelector("[type='search']")
        ?.focus()
    },
  }],
})

handle.update([/* … */])
handle.dispose()

Guarantees

  • Session-only — scoped to the tab, top-frame document, and origin; never persisted.
  • Non-privileged — no browser APIs, no permission requests, no global keybindings.
  • Validated — strict Zod schema, capped counts and depth, safe icons, protocol allow-list.
  • Same rules as built-ins — site commands respect URL rules, favorites, and ranking.

Tech stack

Core

  • WXT — MV3 build, manifest generation, Chrome + Firefox targets
  • React + Redux Toolkit — UI and state
  • CMDK — list rendering and keyboard nav (shouldFilter={false}; ranking is server-side)
  • shadcn/ui — dialog and form primitives, portal-aware for the shadow root

Validation & utilities

  • Zod — message, settings, and document validation
  • ts-pattern — message routing
  • mathjs (hardened) — calculations, background-only
  • date-fns · Intl — snippet dates, time conversions
  • TypeScript (strict) · Biome · Vitest
Build from source

corepack enable (pins pnpm 11), then pnpm install. Develop with pnpm run dev:chrome or dev:firefox; build with pnpm run build / build:firefox. Type-check with pnpm run tsc, test with pnpm test.
