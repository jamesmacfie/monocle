Integrations

A command layer other tools plug into.

Monocle can cross the extension boundary through explicit, revocable integrations. The Native Bridge and Raycast client are still developer-facing; peer-extension support and the page SDK are implemented but remain approval- or session-scoped.

  • Native bridge

Raycast

Run your tab from Raycast.

The private-development Raycast client can search commands supplied by the active non-incognito browser tab through Native Bridge. It reuses Monocle's query and execution paths, but it does not expose page-SDK commands and is not yet distributed as a public Raycast Store extension.

  • Pair once. A Bluetooth-style pairing code links Raycast to a running browser; each client gets its own token you can revoke.
  • Active-tab aware. Suggestions, search, and nested groups reflect the eligible active tab. Incognito and page-SDK-only command sources are excluded.
  • Runs the real command. Execution happens in the browser's background worker only after the separate Allow execution opt-in. Confirm-gated, automation, and debug commands remain denied.

A bridge that runs on your machine.

A browser extension can't open a socket for an app to dial into, so Monocle ships a small native helper. The Raycast extension talks to it over loopback HTTP; the helper relays through a Unix-domain socket and browser native messaging. The transport remains on the local machine and the feature is off by default.

  • Layered opt-in. Enable the feature, grant nativeMessaging, pair a client, then separately allow command execution if wanted.
  • Local transport. Loopback HTTP, a Unix socket, and native messaging — no Monocle cloud endpoint.
  • Token-gated. Each client receives a bearer token; the extension stores its hash and lets the user revoke that client.

Extension to extension

Other extensions can join your palette.

A peer browser extension can register its own commands straight into Monocle. You approve it once on the Integrations settings page — then its commands behave like any built-in: they're searchable, bindable to a shortcut, hideable per site, and favoritable. When one runs, Monocle sends a request over a runtime port and returns the peer's response to the palette flow; the peer does its work in its own extension context.

  • You approve each one. The browser-verified extension id is the identity — no pairing code, and nothing shows up until you say yes.
  • Contained. A peer can add commands, not permissions. It can't make Monocle perform privileged browser work, and it receives no tab URL or page content from Monocle.
  • Always there. Approved commands are cached, so they render in the palette even while the peer is asleep.

window.Monocle

And any page can join in.

The same idea works from inside a web page. Through window.Monocle, a site can register session-only commands — open its search, jump to a section, run a saved query — with no extension permissions and no build step. It's the site SDK that extension-to-extension generalises.

page javascript
window.Monocle.commands.register({
  namespace: "docs",
  name: "Docs",
  commands: [{
    id: "open-search",
    type: "action",
    name: "Open Site Search",
    onExecute() {
      document
        .querySelector("[type='search']")
        ?.focus()
    },
  }],
})
You're in control of every connection

Each integration is opt-in and revocable. The Native Bridge stays on the local device; peer extensions and paired clients appear only after approval. Monocle accepts declarative command descriptions and never evaluates page- or peer-supplied JavaScript inside extension context. The page or peer still runs its own implementation in its own context.
