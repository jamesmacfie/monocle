Automations / How automations work

How automations work

An automation is a declarative document, not a program. You describe the work — the steps, the variables, the conditions — and Monocle's background engine carries it out, handing the DOM work to a content script running in your page. Understanding that split is the key to writing automations that behave predictably.

The execution pipeline

Whether an automation starts from the palette, a keybinding, a matching page, or a schedule, every run unfolds the same way. The background service worker coordinates; the content script touches the page.

  1. A trigger fires — a manual selection, a page that matches the scope, an element that appears, an interval, a schedule, or browser startup.
  2. The engine reads the stored document by id. It always reads fresh from storage, so the run reflects the document as it exists now, not a cached copy.
  3. Variables are interpolated in the background — {{var}} templates, snippet bodies, and trigger context are expanded before the page is involved.
  4. Contiguous content steps batch into a segment, are lowered to a workflow, and run in order in the page.
  5. Engine ops run between segments — navigate, clipboard, httpRequest, runCommand — and conditions evaluate against live page state as branch, forEach, and while are reached.
  6. Results aggregate across segments. The run returns a success or error, and its configured toast can report the outcome.
  7. Text captured by getText feeds later steps — into conditions, templates, and clipboard writes downstream.

Segmentation

The engine doesn't ship your steps to the page one at a time. It partitions them: a run of content (DOM) steps batches into a single segment that executes in the page in order, and an engine step interrupts between segments to run in the background. The next segment of content steps follows, and so on. 

[content step, content step, content step]   ← segment 1 (runs in page)
[engine step]                                ← runs in background
[content step, content step]                 ← segment 2 (runs in page)
[branch → content steps inside]              ← segment 3 (branches recurse)
[getText]                                    ← end of segment 4, extract vars
[engine step]                                ← engine op with extracted vars

This partition is what makes the model work. Template and snippet resolution, clipboard writes, network requests, and branch decisions stay in the background. Final values needed by a page step are sent to the content executor, so a resolved credential used to fill a form necessarily reaches that page. Because a segment returns its results before the next engine step runs, a getText result is available to feed the very next condition: fill a form, submit, wait for the response page, read the confirmation text, then copy it.

Interpolation happens in the background

Every interpolatable field — fill.text, setVariable.value, toast.message, navigate.url, and permitted httpRequest value fields — is expanded in the background, before the content script sees anything. {{var}} templates and snippet placeholders are resolved into plain strings up front.

The content executor never learns templating. It receives finished values and sets them on the page. And one field type is never interpolated: selectors (along with CSS bodies and URL patterns). They are addresses, not data — a templated selector would be unreviewable in an import summary, so it is a hard boundary.

Data, not code

A hard boundary

There is no eval, no new Function, and no arbitrary-JavaScript step in the current schema. An automation is a structured document with fixed verbs and capped nesting: configuration, not a program. That constraint makes behavior easier to inspect and review, but imported automations still deserve scrutiny: they can modify pages, navigate, write the clipboard, and make explicitly configured network requests.

The document shape

Every automation is a stored document with a fixed shape. The id doubles as the generated palette command id; the rest describes presentation, scope, when it runs, the values it uses, and the work itself. 

{
  "id": "9f8e7d6c-…",                    // UUID; becomes the command id
  "schemaVersion": 1,
  "name": "Auto-fill login",             // 1–100 chars
  "description": "Optional narrative",   // 1–2000 chars
  "icon": "LogIn",                       // Lucide icon name
  "color": "teal",                       // preset color
  "enabled": true,                       // master switch
  "urlRules": {
    "allowUrls": ["dev.example.com"],    // pages it may touch
    "denyUrls": []                       // pages it must not
  },
  "triggers": [{ "type": "manual" }],    // when it runs
  "vars": {                              // named values
    "user": { "kind": "snippet", "snippetId": "a1b2…" },
    "password": { "kind": "snippet", "snippetId": "c3d4…" }
  },
  "steps": [                             // the work
    { "op": "fill", "target": { "strategy": "css", "value": "#username" }, "text": "{{user}}" },
    { "op": "click", "target": { "strategy": "text", "value": "Sign in" } }
  ],
  "options": {
    "showResultToast": true              // show the success/error toast
  }
}

Concurrency

One run at a time

Only one run of a given automation happens per tab at once. If a trigger fires while that script is already running on the tab, the re-entrant run is dropped, not queued. Non-manual runs of the same script on the same tab also observe a 5-second cooldown between fires, which keeps a noisy page or a tight interval from starting a trigger storm.
