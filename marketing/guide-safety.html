Limits, safety & sharing

Automations are powerful, but they're bounded on purpose. Every limit on this page exists for one reason: so a runaway loop, a buggy selector, or a script you imported from someone else can't quietly cause harm. The guardrails are enforced when you save and re-checked when a script actually runs.

Execution caps

These are the hard ceilings on what a single automation can be and do. They keep documents small enough to review and runs short enough to stay safe.

Limit Value
Scripts per browser 200
Steps per script (including nested) 100
Control-flow nesting depth 3
Loop iterations (per loop) 50 default, hard max 1000
Total executed steps per run 5000 (runaway protection)
Triggers per script 5 (at most one of each non-manual type)
Variables 50
Manual-trigger parameters 10
String fields ≤2000 chars
CSS / clipboard bodies ≤10000 chars
Regex patterns ≤200 chars, no user-supplied flags
Checked twice

Every cap is enforced when you save a document and re-checked by the engine at run time. A script that somehow slips past one gate still stops at the other.

Structural rules

A few rules aren't about size — they're about keeping the execution model coherent. These constraints are what let the engine reason about a run with confidence:

  • Navigation can't live inside branches or loops. navigate (or openUrl with currentTab) destroys the content context, so it's only allowed at the top level of a flat script — never inside a branch or loop body.
  • One concurrent run per script per tab. If a trigger fires while the script is already running on that tab, the new run is dropped, not queued.
  • A 5-second cooldown between non-manual runs of the same script on the same tab, so a trigger storm can't hammer a page.
  • Imported scripts arrive with non-manual triggers disarmed. Nothing fires on its own until you explicitly arm it in the editor.

What automations cannot do

The most important guarantees are the things an automation simply can't express. This is a deliberate boundary, not a missing feature:

Hard boundaries

No arbitrary JavaScript. There is no eval, no new Function, and no runJs step — and there never will be. It's a policy boundary, not an oversight.

No page mutation outside the prescribed steps. A script can only do what the fixed step vocabulary allows; it can't create or run code on the page.

No remote code. Every step comes from the stored document — never fetched from the network at run time.

No data exfiltration. Automations don't phone home. clipboardWrite and openUrl are the only outbound actions, and both are surfaced in the import review.

The credentials caveat

Automations can fill login forms by pulling a username and password from snippets. That's genuinely useful — and it comes with one honest warning.

Read this before storing a password

Snippet-backed credentials live unencrypted in chrome.storage.local. Monocle encrypts nothing itself; it relies on the browser and operating system for disk encryption.

Use this only for low-stakes dev and test credentials. For high-value accounts, reach for a real password manager with autofill — not an automation.

Credentials are interpolated in the background and are never logged; they reach the page only through the fill step's native value-setter.

Import & export

Sharing an automation is just moving a JSON document — and the importer treats anything from outside as untrusted until you say otherwise.

Import

Drop a JSON file into the importer. Monocle strips the id and timestamps, validates the rest, and disarms every non-manual trigger. Before anything is saved, a review dialog lays out exactly what the script would do:

  • Every URL pattern in its scope
  • Each trigger's type and fire condition
  • An op-class summary (click, fill, branch, and so on)
  • Snippets it references
  • URLs it would open
  • Clipboard and command usage

You save the script only after you've reviewed that summary.

Export

Export saves the document as JSON. Note what's not in the file: keybindings, favorites, and per-command URL-rule overrides are left out, because they live in command settings rather than the automation document itself.

Runtime limits at a glance

The limits that bite during an actual run, in one place:

  • Concurrency — one concurrent run per script per tab.
  • Cooldown — 5 seconds between non-manual runs of the same script on the same tab.
  • Runaway cap — 5000 executed steps per run.
  • Loops — 50 iterations by default, hard max 1000.
  • Timeouts — wait steps default to 5 seconds; navigation has a 15-second maximum.

Exceed any of these and the run stops with an error toast — it never fails silently.
