Automations / Steps & operations

Steps & operations

Every automation is a list of steps, run in order. Each step does one thing. Steps come in two flavours: content steps are DOM actions that run inside the page — click a button, fill a field, read some text. Engine steps are privileged operations and control flow that run in the background, in between the content segments — navigate, copy to the clipboard, branch, loop. The engine batches contiguous content steps into one segment, runs them in the page, then takes back over for the next engine op.

Page steps

These are page-side DOM interactions. They arrive at the content script with every variable already expanded — there is no templating in the page.

Op What it does
clickClick an element — left/middle/right button, single or double, with optional modifier keys.
waitPause until a condition holds: a simple sleep (timeMs), an element reaching a state, a urlIncludes change, or document readyState.
fillSet an input's value the way the page expects it (React, Vue, plain DOM), with a configurable clear mode and fired events.
typeSimulate keystrokes one at a time — lower fidelity than fill, but works in exotic editors.
keySend a key combo (e.g. Control + A) to the active element.
selectChoose a <select> option by value, label, or index.
check / uncheckSet a checkbox to a known state (idempotent).
submitSubmit a form; if the target isn't a form, submits its closest enclosing form.
hoverHover an element — e.g. to reveal a dropdown.
focus / blurMove keyboard focus onto or off an element.
scrollScroll the window or an element to top/bottom/center, to coordinates, or into view; auto or smooth.
getTextRead an element's text or an attribute into a variable for later steps.
removeElementRemove an element from the page (destructive). Optionally remove every match.
hideElementHide an element via a scoped display: none rule (reversible — reload to undo).
injectCssInject a block of CSS into the page under a scope key.

A few representative steps:

- op: click
  target: { strategy: "text", value: "Sign in" }
  button: "left"
  modifiers: ["Control"]   # Alt | Control | Meta | Shift
- op: fill
  target: { strategy: "css", value: "input[name='email']" }
  text: "{{email}}"
  clear: "select-all"      # "select-all" (default) | "backspace" | "none"
  fire: { input: true, change: true }
# Wait for an element to disappear…
- op: wait
  for: { selector: { strategy: "css", value: ".spinner" }, state: "hidden" }
  timeoutMs: 5000

# …or wait for a simple sleep / URL change
- op: wait
  for: { urlIncludes: "dashboard" }
- op: getText
  from: { strategy: "css", value: "h1" }
  attr: "textContent"      # "textContent" (default) | "value" | any attribute
  toVar: "pageTitle"
getText, hide vs remove

getText reads an element's text (or a named attribute) into a variable so later steps can interpolate it — the captured value is returned in the workflow result only and is never logged. hideElement is reversible: it injects a scoped CSS rule, so a reload brings the element back. removeElement is destructive — it deletes the node outright.

Engine operations

Engine steps run in the background between content segments. They handle navigation, the clipboard, notifications, surfaces, and messaging. Their interpolatable fields (URLs, text, messages) are expanded background-side before use.

Op What it does
setVariableSet a runtime variable to an interpolated value for use in later steps.
toastShow a brief notification — success, error, or info.
navigateNavigate the script's pinned tab to a URL and wait for load (15s max). Destroys the content context — see the note below.
openUrlOpen a URL with a disposition of newTab (default), currentTab, or newWindow.
clipboardWriteCopy interpolated text to the clipboard.
insertSnippetInsert a snippet at the page's last-focused editable, or fill a target with it; placeholders are interpolated.
showSurface / hideSurfacePush or remove a declarative UI surface. Automations can only produce overlay and badge kinds (not modal or picker).
runCommandExecute another Monocle command — subject to the policy below.
 
- op: setVariable
  name: "result"
  value: "{{heading | trim}} at {{trigger.url}}"

- op: clipboardWrite
  text: "Heading: {{heading}}\nURL: {url}"

- op: toast
  level: "success"          # "success" | "error" | "info" (default: "info")
  message: "Saved {{count}} records"
- op: openUrl
  url: "https://www.google.com/search?q={{params.query | encodeUriComponent}}"
  disposition: "newTab"     # "newTab" (default) | "currentTab" | "newWindow"
navigate is flat-only

navigate destroys the page's content context, so it cannot run inside a branch or loop body — only at the top level of a flat script. The same restriction applies to openUrl with currentTab. Putting navigation inside control flow would fragment the engine's flow state, so it is forbidden.

runCommand & its policy

runCommand lets an automation execute another Monocle command by id — for example, to reload the tab or copy the current URL. Because it crosses into the rest of the command system, it is tightly policed. 

- op: runCommand
  commandId: "copy-current-url"
runCommand policy

Always denied, for every run: commands that require confirmation, other user scripts (no recursion), and the debug-workflow tool.

For non-manual runs (anything fired by a trigger), runCommand is further restricted to a static allowlist of navigation, tab, and read-only commands. Manual runs may call any non-denied command; triggered runs may call only these:

go-back go-forward go-to-parent-url go-to-root-url reload-current-tab hard-reload-current-tab scroll-to-top scroll-to-bottom open-new-tab duplicate-current-tab focus-next-tab focus-previous-tab focus-first-tab focus-last-tab focus-last-active-tab toggle-pin-current-tab toggle-mute-current-tab copy-current-url copy-current-title copy-title-and-url copy-title-and-url-as-markdown focus-first-input

Control flow

Three engine ops shape how steps run: branch chooses a path, forEach repeats over a list, and while repeats while a condition holds. All three are evaluated in the background with live page state, so a condition can react to what the page actually looks like at that moment.

branch

Run one set of steps or another depending on a condition. The else arm is optional. 

- op: branch
  if: { kind: "elementExists", selector: { strategy: "css", value: ".error-message" } }
  then:
    - op: toast
      level: "error"
      message: "Form has errors"
  else:
    - op: submit
      target: { strategy: "css", value: "form" }

The condition kinds:

Kind True when…
elementExistsThe selector matches anything on the page.
elementVisibleThe selector matches and the element is visible.
elementTextThe element's text compares against a value. Operators: equals, equalsIgnoreCase, notEquals, contains, notContains, startsWith, endsWith.
urlIncludesThe current URL contains the given string.
varCompareA variable compares against a value. Operators: all of the elementText operators, plus greaterThan and lessThan (numeric).
varMatchesA variable matches a regular expression (pattern ≤ 200 chars, no flags).
notLogical NOT of another condition (of).
allOfLogical AND of 1–10 conditions.
anyOfLogical OR of 1–10 conditions.

forEach

Repeat a body of steps once per item. Loop over the elements a selector matches, or over the lines of a variable. as names the loop variable (default item) and maxIterations caps the count (default 50). 

- op: forEach
  over: { elements: { strategy: "css", value: "input[type='checkbox']" } }
  as: "item"
  maxIterations: 50
  steps:
    - op: check
      target: { strategy: "css", value: "input[type='checkbox']" }
Pinning & loop scope

Inside the loop, {{item}} (or your as name) holds the current element's text and {{index}} holds the 0-based iteration number; both are scoped to the body and restored afterwards. Pinning is the convenient part: a body step whose selector is exactly the loop's selector is automatically bound to the current item — so the check above ticks each checkbox in turn, with no templating needed.

Or iterate a variable's lines:

- op: forEach
  over: { variable: "emailList" }
  as: "email"
  steps:
    - op: fill
      target: { strategy: "css", value: "input[type='email']" }
      text: "{{email}}"

while

Repeat the body while a condition stays true, up to maxIterations. Ideal for "click until it's gone" patterns like pagination. 

- op: while
  condition: { kind: "elementExists", selector: { strategy: "text", value: "Load more" } }
  maxIterations: 10
  steps:
    - op: click
      target: { strategy: "text", value: "Load more" }
    - op: wait
      for: { timeMs: 500 }

Step values come from variables, and elements come from selectors — see Variables & selectors for {{var}} templates, pipes, and the two selector strategies. For loop caps, nesting depth, and the runaway protections that bound all of this, see Limits, safety & sharing.
