Automations

Teach your browser the things you do twice.

Automations are the repetitive web tasks you do every day — filling a login, clicking through a flow, dismissing a banner, scraping text to your clipboard — captured once and replayed on a keystroke, a page load, or a schedule.

Start the guide See the cookbook

Data, not code.

An automation is a structured document — fields, steps, and conditions with a fixed set of verbs and capped nesting. There is no eval, no JavaScript, and no arbitrary-code step, and there never will be.

That single decision is what makes automations safe to share, trivial to review before you run them, easy to debug, and compliant with the Chrome Web Store and Firefox AMO. You can read exactly what one will do before it does it.

steps:
  fill   #username  → {{user}}
  fill   #password  → {{pass}}
  click  "Sign in"
  wait   url ⊃ "/dashboard"
  toast  "Logged in ✓"

How a run unfolds

The background service worker coordinates; the content script does the DOM work. Sensitive operations stay in the background and are never logged.

  1. A trigger fires. You pick the automation from the palette, press its shortcut, or a page-load / element / schedule trigger arms it.
  2. The engine reads the document by id and re-validates its structure before running anything.
  3. Variables are interpolated in the background. {{var}} templates, snippet placeholders, and page context are all resolved here — the page never learns templating.
  4. Contiguous DOM steps batch into a segment and run in the content script as one workflow: click, fill, wait, getText, hide, and the rest.
  5. Privileged ops run between segments in the background — navigate, clipboard, run another command, show a surface — and conditions are evaluated against live page state.
  6. Results aggregate and a success or error toast closes the loop. Extracted text feeds into later steps.

Six ways to trigger

When an automation runs.

  • Manual — from the palette or a keybinding, optionally with a form of parameters.
  • URL match — when a matching page loads or navigates (SPA-aware).
  • Element appears — when a selector first shows up on the page.
  • Interval — every N minutes via the alarm system.
  • Schedule — daily at a local time.
  • On startup — when the browser starts.

A vocabulary of verbs

What an automation can do.

  • Page steps — click, fill, type, key, select, check, submit, hover, focus, scroll, wait, getText, hideElement, removeElement, injectCss.
  • Engine ops — setVariable, toast, navigate, openUrl, clipboardWrite, runCommand, insertSnippet, showSurface.
  • Control flow — branch (if/else), forEach, while, with conditions and capped loops.

The options builder ships a set of example automations covering every trigger type and most of the step vocabulary. Add them with one click and edit from there.

A few things you can build

Each of these is a handful of declarative steps.

Auto-fill a dev login

Keep credentials in snippets, fill the form, click sign-in, wait for the dashboard, and toast success — bound to a shortcut you can fire from the login page.

Dismiss cookie banners

An element appears trigger watching for “Accept all” clicks it the moment it shows up, with a manual fallback.

Scrape a heading to the clipboard

getText the page's h1, format it with the URL and a timestamp, and write the lot to your clipboard.

Click “Load more” until it's gone

A while loop clicks the pagination button and waits, capped at a safe number of iterations, until the page is fully expanded.

Built to be trusted

Automations can't run arbitrary JavaScript, can't reach the network, and can't phone home — clipboardWrite and openUrl are the only outbound actions, and both show up in the import review. Runs are capped (one per script per tab, bounded loops, a 5,000-step ceiling), and imported documents land disarmed. Limits, safety & sharing →
